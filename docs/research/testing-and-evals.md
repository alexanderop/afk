# Testing afk: evals, regression detection, and CI tiering for a markdown-product plugin

## 1. TL;DR

**Should afk have an eval suite? Yes — but not a framework.** Anthropic's own docs state plainly: "There is not currently a built-in way to run these evaluations. Users can create their own evaluation system" ([Agent Skills best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)). The reference implementation for exactly afk's product type is already cached on this machine: the official skill-creator plugin at `/Users/alexanderopalic/.claude/plugins/cache/claude-plugins-official/skill-creator/unknown/skills/skill-creator/` ([source repo](https://github.com/anthropics/skills/tree/main/skills/skill-creator)) — markdown judge agents (`agents/grader.md`, `agents/comparator.md`, `agents/analyzer.md`), JSON schemas for evals/grading/benchmarks, and a small stdlib-Python aggregator (`scripts/aggregate_benchmark.py`) that is just mean/stddev arithmetic, trivially portable to bash+jq. Port the pattern, not a framework. (If you ever want a framework anyway, [promptfoo](https://www.promptfoo.dev/docs/providers/custom-script/) is the only mainstream one that runs via `npx` with zero repo footprint and has both an `exec:` shell provider and a [native claude-agent-sdk provider](https://www.promptfoo.dev/docs/providers/claude-agent-sdk/) that loads local plugins and exposes `metadata.skillCalls` plus a deterministic `skill-used` assertion. Inspect AI, DeepEval, evalite, Braintrust all drag in Python/node/SaaS dependencies that violate the repo's constraints.)

**What can be automated:** structural quality of every artifact (PRD sections, slice ticket shape, QA evidence blocks, review severity vocabulary) with zero-token grep/jq; trigger *rates* over k runs; final-worktree outcome checks on fixture repos (`verify.sh`, terminal-bench style); mutation score of generated test suites; review recall against real historical bug-fix commits. LLM judges are reserved for genuinely subjective substance, decomposed into binary checks.

**How to know a prose change made things better or worse:** snapshot the old skill (`cp -r skills/spec workspace/skill-snapshot/`), run the *same* eval prompts through old and new in clean contexts, 3+ runs per configuration, grade both with the same assertions, and hand artifact pairs to a *blind* comparator agent that doesn't know which version produced which. The headline output is a paired delta row (pass_rate, time, tokens) as mean ± stddev — that delta IS the answer. This is skill-creator's documented protocol for editing existing skills (its SKILL.md, "Spawn all runs" / "Advanced: Blind comparison"). One run is never an answer: single-run pass@1 swings 2.2–6.0 percentage points run-to-run even at temperature 0 ([On Randomness in Agentic Evals](https://arxiv.org/abs/2602.07150)).

**What stays manual:** nobody runs LLM tests per-commit. [obra/superpowers has zero CI workflows](https://github.com/obra/superpowers) (documented cost: ~$4.67 and 10–30 min per integration run); [aider's benchmark](https://github.com/Aider-AI/aider/blob/main/benchmark/README.md) is manual with committed YAML results keyed by git hash; [OpenHands gates evals behind a PR label](https://github.com/All-Hands-AI/OpenHands/pull/4489). And Anthropic insists on human transcript reading: "we do not take eval scores at face value until someone reads transcripts" ([Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

## 2. The testing pyramid for a markdown-product plugin

| Layer | What it is | afk today | Gap |
|---|---|---|---|
| 0. Deterministic checks on the markdown itself | Frontmatter schema, line budgets, link integrity, rubric sync | Hook tests + shellcheck in `tests/hooks/` and `.github/workflows/checks.yml`; severity-rubric sync hook test exists | Frontmatter lint (skill-creator ships `scripts/quick_validate.py` as the model — name/description presence, description length), per-file line budgets (skill-creator's own rule: SKILL.md under 500 lines), dead relative-link check across `skills/`/`agents/`, `claude plugin validate` |
| 1. Plugin-load smoke | One `--max-turns 1` headless run asserting the plugin loaded | Missing | The stream-json `system/init` event reports `plugins` and `plugin_errors`; the [headless docs](https://code.claude.com/docs/en/headless) say verbatim "Use the plugin fields to fail CI when a plugin did not load." Costs pennies, catches manifest/frontmatter breakage |
| 2. Triggering | Naive prompts → did the right Skill call appear | `tests/skill-triggering/` exists, with negatives | Single-shot → upgrade to 3 runs/prompt with a rate threshold (skill-creator's `run_eval.py` defaults: `--runs-per-query 3`, `--trigger-threshold 0.5`); add `--bare` for hermeticity; early-exit on first tool call (first tool ≠ Skill = definitive negative, cuts cost); near-miss negatives ("don't make should-not-trigger queries obviously irrelevant" — skill-creator SKILL.md); a `--model haiku` stress variant (superpowers' `run-haiku-test.sh`: "tests whether a cheaper/faster model fails more easily"); an explicit-skill-request suite and multiturn variants (superpowers has both; afk has neither) |
| 3. Behavioral / parity | Assertions on transcripts; Claude Code × Copilot CLI matrix | `tests/claude-code/`, `tests/parity/` exist | Pressure-scenario tests for discipline skills (sizing gate, forced TDD): obra's doctrine is no skill edit without a failing baseline run first, then assert the gate holds under combined pressures (deadline + sunk cost + authority) ([testing-skills-with-subagents](https://github.com/obra/superpowers/blob/main/skills/writing-skills/testing-skills-with-subagents.md)). End-to-end behavioral assertions like superpowers' integration test (subagents dispatched, NO scope creep, review ordering) |
| 4. Artifact quality evals | Grade what the skills *produce* | Missing entirely | `tests/evals/`: per-skill `evals.json` (prompt + assertions), grader agent, golden *inputs*, structural greps + binary-rubric judges — Section 3 |
| 5. Outcome benchmark (with/without plugin) | Paired A/B on realistic tasks, objective oracle | Missing | Fixture repos + hidden `verify.sh` + paired stats — Sections 3–4 |

One parity constraint shapes layers 4–5: **Copilot CLI's programmatic mode has no json/stream-json output, no plugin loading, and an unstable flag surface** (`--headless --stdio` was removed without deprecation, [github/copilot-cli#1606](https://github.com/github/copilot-cli/issues/1606); [programmatic reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-programmatic-reference)). So the portable quality layer must grade **on-disk artifacts and final worktree state**, never transcripts. Trajectory assertions (skillCalls, tool order, token counts) are a Claude-Code-only tier, permanently.

## 3. Measuring quality, not just triggering

The grader hierarchy, per [Anthropic's empirical-evals guidance](https://platform.claude.com/docs/en/test-and-evaluate/develop-tests): code-based first ("fastest and most reliable"), LLM-based second ("test to ensure reliability first"), humans last. "Prioritize volume over quality: more questions with slightly lower signal automated grading is better than fewer questions with high-quality human hand-graded evals."

### Code-graded structural checks (free, harness-portable, CI-able)

- **PRD from `afk:spec`:** required sections present; every requirement has an acceptance criterion line; open-questions section exists; greppable.
- **Tickets from `afk:slice`:** each slice ticket contains UI + API + test sections; count of slices > 1; each ticket independently parseable.
- **QA report:** TC sections present; every claim has an evidence path/block.
- **Review verdict:** every severity drawn from the allowed vocabulary in `skills/review/reviewer-shared.md` (extends the existing sync hook-test); every finding cites file:line.

These run identically under `claude -p` and `copilot -p` because they only read files — they become the quality extension of `tests/parity/`.

### Golden inputs, not golden outputs

Reference-based golden-output grading breaks down for long-form documents — many different texts are equally correct ([Evidently, LLM-as-judge guide](https://www.evidentlyai.com/llm-guide/llm-as-a-judge)). Instead freeze the **inputs**: one golden PRD fed to `afk:slice` makes slice quality comparable across runs; one seeded fixture repo holds the substrate constant so a prose change in one skill is isolated from upstream variance.

### LLM-as-judge, hardened

Per-skill expectation lists in `evals.json`, graded by an afk-local grader agent ported from skill-creator's `agents/grader.md`, which has the anti-gaming rules worth copying verbatim: evidence-cited PASS/FAIL per assertion, "burden of proof to pass is on the expectation," superficial compliance fails, no partial credit — and the grader *critiques the eval set itself*, flagging assertions that "would also pass for a clearly wrong output." Judge-design rules from the [bias literature](https://www.evidentlyai.com/llm-guide/llm-as-a-judge): decompose into **binary** checks rather than 1–10 scores ("73 vs 82" is noise); for pairwise comparisons run **both A/B orderings** and count only consistent verdicts (position bias is ~10% and "not optional" to mitigate); pin the judge model id; force reasoning then discard it; use a different model family to grade than to generate. afk's existing severity rubric is already the kind of detailed rubric judges need — reuse it as the judge rubric so product and eval stay in sync.

### Blind comparison for prose changes

Skill-creator's `agents/comparator.md`: the judge sees two outputs labeled only A/B — "you do NOT know which skill produced which. This prevents bias" — generates a task-specific 1/3/5 rubric (correctness, completeness, accuracy / organization, formatting, usability), and must be decisive ("ties should be rare"). An analyzer then unblinds and explains *why* the winner won with quoted evidence. This is the mechanism for subjective deltas (is the new PRD clearer? is the review verdict more useful?) where assert_contains can't judge.

### Objective oracles that need no judge at all

- **Mutation score for the TDD claim.** afk's core sales pitch — forced red-green-refactor produces better tests — is invisible to "hidden tests pass" (both conditions often pass). Mutation testing is the established stronger oracle: coverage is a weak fault-detection indicator while mutation score is the stringent one ([LLM test-generation benchmark](https://arxiv.org/pdf/2508.00408), [MUTGEN](https://arxiv.org/pdf/2506.02954)). Ship Stryker/mutmut config *inside each fixture repo* (a dev-dependency of the fixture, not of afk — preserves the no-package-manager constraint), run it in `verify.sh` after the pipeline, report killed/total per condition.
- **Review recall on real bugs, not planted ones.** LLM-injected bugs have a documented validity problem: "no evidence that synthetic bugs match the distribution or subtlety of real defects," and LLM-inject-plus-LLM-judge is circular ([DeepSource](https://deepsource.com/blog/ai-code-review-benchmarks), critiquing [Qodo's benchmark](https://www.qodo.ai/blog/how-we-built-a-real-world-benchmark-for-ai-code-review/)). Protocol: harvest 10–20 real bug-fix commits (afk's own `.afk/brain/` and the maintainer's projects are the sourcing pool — "tasks drawn from real failures" is the official advice), check out the pre-fix state, run `afk:review`, grade recall mechanically: did any finding cite the file/line region the real fix touched? Report **precision too** — the dominant failure mode of review agents is high precision with very low recall, and a prose change that makes reviewers chattier inflates recall while precision collapses.
- **TDD-actually-happened check:** the agent's generated tests pass AND fail when the implementation is reverted; plus a trajectory check (Claude-only tier) that the test file was committed before the implementation.
- **Side counters from the transcript**, aider-style: tokens, wall-clock, turn count, whether a spec file was produced, commit atomicity. Always report cost next to quality as a Pareto pair — "AI Agents That Matter" ([Princeton](https://arxiv.org/pdf/2407.01502)) shows agent gains often come from retry-spam that only a cost axis exposes. The pipeline deliberately spends more tokens; the eval must show what that buys.

## 4. Regression detection under nondeterminism

**The noise floor.** [On Randomness in Agentic Evals](https://arxiv.org/abs/2602.07150) (60,000 SWE-bench Verified trajectories): single-run pass@1 varies **2.2–6.0pp** depending on which run you pick, stddev >1.5pp even at temperature 0; trajectories diverge within the first few percent of tokens. A single with/without run differing by one task in ~30 is indistinguishable from noise. House rules from the field: [SWE-rebench](https://arxiv.org/abs/2505.20411) runs 5 times per task and reports mean ± SEM; [METR](https://evaluations.metr.org/faq/) runs 6 and still sees bootstrap CIs up to ~50pp wide in worst cases. **Adopt: 5 runs per task per condition for benchmarks, 3 for trigger evals (skill-creator's own default), mean ± stddev always.**

**Paired design is what makes a hobby budget viable.** Independent arms detecting a 4pp delta need ~1,580 examples per arm; the same tasks run through both conditions analyzed with [McNemar's test on discordant pairs](https://jameshoward.us/2024/12/17/mcnemars-test-the-hidden-gem-for-paired-binary-data) cut that ~10x ([power math](https://dev.to/gabrielanhaia/eval-set-sizing-the-statistical-power-math-behind-llm-ab-tests-4gpc)). Anthropic's [error-bars paper](https://arxiv.org/abs/2411.00640) says the same: compare via paired differences on the same questions; naive SEs can be 3x too small. Even paired, ~30 tasks × 5 runs detects only **large** effects (~10pp+) — so design metrics with large expected deltas (categorical behaviors: "failing test written first, yes/no") and treat judge-score deltas as a dashboard, never a merge gate.

**pass@k vs pass^k** ([tau-bench](https://arxiv.org/abs/2406.12045)): pass@k (≥1 of k) measures capability; pass^k (all k) measures reliability — 75% per-trial → (0.75)³ ≈ 42%. afk runs unattended, so reliability is the product. Use **pass^k for must-never-fail behaviors**: the sizing gate routes big tickets to the pipeline, small tickets NEVER trigger it (upgrade the existing negative tests from pass@1 to pass^k), severity vocabulary adherence.

**Baselines.** Two kinds, both from skill-creator: *no-plugin* baseline for "does afk earn its tokens" (same prompt, `--plugin-dir` on vs off, throwaway fixture repo per trial, clean isolated environment); *old-prose snapshot* baseline for "did this edit regress" (`cp -r` the skill before editing, run both versions in the same turn). Curate tasks aider-style: [aider's polyglot rebuild](https://aider.chat/2024/12/21/polyglot.html) discarded 258 problems all models solved and 66 none solved — only sometimes-pass tasks carry signal. Pilot candidates against the no-plugin baseline and keep the ones it passes sometimes-but-not-always.

**Goodharting is afk's central hazard** — the product *is* the prompt. Measured: shallow prompt optimization lifted dev-set accuracy 0.40→0.80 but held-out test only 0.20→0.50 — half the gain was overfitting ([RLHF book, over-optimization](https://rlhfbook.com/c/14-over-optimization)). Skill-creator's own description optimizer splits queries 60/40 train/held-out and selects by **test** score. So: keep a held-out task set never consulted while editing SKILL.md prose, rotate it across releases, build tasks from post-cutoff material, and keep `verify.sh` out of the agent's worktree (run it post-hoc in a clean checkout) — models have been caught reading graders and stubbing evaluation functions.

**Flakes:** an eval at "50% ± 40%" is a broken task to fix, not noise to average away (skill-creator's analyzer flags exactly this, plus non-discriminating assertions that pass in both configs). Quarantine persistently flaky prompts (skipped from gating, still reported) rather than rerunning until green.

## 5. CI tiering and cost

**Urgent context:** starting **June 15, 2026** (four days from now), `claude -p` on subscription plans draws from a separate monthly Agent SDK credit — Pro $20, Max 5x $100, Max 20x $200 ([support article](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)). Local LLM-test runs now have a hard monthly budget; CI should authenticate with `ANTHROPIC_API_KEY` (or [OIDC federation, as anthropics/claude-code-action does](https://github.com/anthropics/claude-code-action/blob/main/docs/setup.md)), never `CLAUDE_CODE_OAUTH_TOKEN`, which ties CI spend to your personal credit pool.

**Hermeticity everywhere:** add `--bare` to every headless invocation — it skips ~/.claude hooks/skills/plugins/CLAUDE.md ("a hook in a teammate's ~/.claude... won't run"), will become the `-p` default, and this machine has dozens of third-party skills competing with afk's for triggering ([headless docs](https://code.claude.com/docs/en/headless)). Exception: the CLAUDE.md-backstop parity test, which injects the template via `--append-system-prompt-file` instead. Always set `--max-turns` in CI.

| Tier | When | What | Cost |
|---|---|---|---|
| Per-edit | every save | `tests/hooks/run-hook-tests.sh` + shellcheck (existing) | $0 |
| Per-PR, in `checks.yml` | every push | Above + frontmatter/line-budget/link lint + `claude plugin validate` + plugin-load smoke: `claude --bare -p 'hi' --plugin-dir . --max-turns 1 --output-format stream-json \| jq` asserting `system/init` lists afk and `plugin_errors` is absent | ~$0.01 |
| Label + path gated | PR labeled `run-evals` AND `paths: ['skills/**','agents/**','hooks/**']` changed (include `labeled` in trigger `types:` or post-open labeling won't fire — [documented gotcha](https://github.com/orgs/community/discussions/26712)) | `tests/skill-triggering/run-all.sh --runs 3 --model haiku` — rate-gated (≥2/3 per prompt), pass^3 for negatives; write `scores.json` (per-prompt rate, `total_cost_usd`, model) as a workflow artifact; jq-diff vs previous run flags drops as investigate-not-fail | ~10× cheaper than sonnet; the [OpenHands pattern](https://github.com/All-Hands-AI/OpenHands/pull/4489) |
| Nightly/weekly (cron or manual) | scheduled | 3–5 dev-set outcome tasks × 3 runs, bash-graded `verify.sh`, mean ± stddev trended — a dashboard, not a gate; plus sampled transcript reading | a few $ |
| Manual, per-release / per-major-prose-change | human-triggered | Full paired with/without A/B on the **held-out** set, 5 runs/task, McNemar on discordant pairs; blind comparator on old-snapshot vs new prose; full parity matrix; results committed as `benchmark-<date>.md` keyed to the afk commit hash (aider's pattern) | superpowers-scale: dollars + tens of minutes per run — document per-suite cost in `tests/README.md` as [superpowers does](https://github.com/obra/superpowers/blob/main/docs/testing.md) ($4.67, 10–30 min) |

**Self-enforcing budget:** every `--output-format json` response includes `total_cost_usd` with a per-model breakdown — have `run-all.sh` sum it, print it, and abort past an `AFK_TEST_BUDGET_USD` env var. No external tooling. Parse `system/api_retry` events (rate_limit, overloaded) to back off rather than fail.
